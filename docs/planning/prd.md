# TBCG 首版产品需求规格（PRD）

## 1. 产品定位

TBCG 是一个原创、内容驱动的 **2D 回合制多人 RPG 框架**。首版目标不是一次性做完整商业 MMORPG，也不是复制既有 xyq 项目，而是交付一条可验证的最小创作与游玩闭环：

> 内容作者提交物品/地图/任务 → Content Reviewer 审核 → Content Publisher 构建并激活 Release → 玩家组队完成多阶段双人副本 → Go 服务端权威结算奖励 → Publisher 可回退后续内容选择。

首版可由同一名操作人兼任 Reviewer 与 Publisher，但 RBAC 权限和操作审计仍分离。

首版必须证明三件事：

1. 玩家能完成原创内容中的多人回合制 RPG 基础体验。
2. 内容作者能在已支持机制内配置新增内容，而不是修改运行时代码。
3. 审核发布者能校验、审批、发布和回退内容快照，且不破坏既有玩家实例。

## 2. 目标用户

### 2.1 玩家

玩家是游戏客户端的最终使用者，关注可玩性、公平性和状态可靠性。

玩家需要：

- 创建或进入角色。
- 进入原创 2D 地图并受控移动。
- 与 NPC 对话并明确接取任务。
- 与另一名玩家组队。
- 进入双人副本或双人战斗。
- 提交回合指令，观看战斗事件表现。
- 获得一次且仅一次的任务、副本或战斗奖励。
- 断线、重连或服务重启后，关键状态可恢复，不重复发奖。

### 2.2 内容作者

内容作者是规则和内容的创建者，关注低代码配置、错误定位和可预览性。

内容作者需要：

- 创建或编辑物品、怪物、基础技能/Buff、NPC、任务、副本等 Definition。
- 在 Godot 中制作原创地图几何、通行格和稳定锚点。
- 在网页管理平台绑定锚点到 NPC、出口、任务目标、怪物遭遇或副本入口。
- 在发布前看到引用错误、字段错误、未支持机制、缺失素材授权等问题。
- 在已有机制范围内新增内容，无需改 Go 或 GDScript。
- 当需要新机制、新交互或新表现时，明确知道必须进入代码扩展流程。

### 2.3 审核发布者

审核发布者负责内容质量、合规、安全和上线控制。首版可以由同一名操作人兼任 Content Reviewer 与 Content Publisher，但审核、批准、构建和激活仍是不同权限/操作；后续可按团队职责拆分，不能因人员兼任而合并审计记录或跳过审批。

审核发布者需要：

- 审查具体 revision，而不是可变草稿。
- 查看内容差异、引用闭包、能力清单、素材来源和校验结果。
- 将通过审核的 revision 构建为不可变 Release。
- 在 staging 环境试玩或验证后激活 Release。
- 激活失败时保留旧 Release 指针。
- 对后续内容选择进行回退，但不撤销已经提交的玩家资产、奖励或货币。
- 查看审计记录，确认是谁在何时修改、审批、构建和激活内容。

## 3. 问题与目标

### 3.1 当前要解决的问题

- 创作链路断裂：地图、规则、任务、战斗和发布缺少统一闭环。
- 内容真源混乱风险：Godot 场景、网页配置和服务端执行容易重复维护同一字段。
- 权威性风险：客户端不能决定奖励、战斗结果、任务完成或经济变更。
- 版本风险：修改模板不能悄悄改变已经存在的玩家资产、任务实例或副本实例。
- 参考项目风险：xyq 只能参考领域语义和工具经验，不能假定协议、存档、素材或实现可直接复用。
- 素材授权风险：没有明确授权的真实素材不能进入可分发首包。

### 3.2 首版产品目标

首版应达成以下目标：

1. 交付一条原创 MVP 可玩闭环：原创地图、NPC、任务、双人战斗/副本和奖励。
2. 建立内容 Definition、运行 Instance、表现 Presentation、发布 Release 的清晰边界。
3. 建立 Godot 与网页管理平台的单向字段所有权：Godot 拥有几何与位置，网页拥有规则绑定。
4. 建立服务端权威执行：Go 服务端决定战斗、任务、奖励、背包和经济结果。
5. 建立 PostgreSQL 唯一数据库约束，首版不做 SQLite/MySQL 多数据库适配。
6. 建立 supported / approximate / unsupported 内容支持门禁，避免静默降级。
7. 为后续 E2E 验收提供可执行、可观察、可重复的用户路径。

## 4. 术语边界

| 术语 | 产品含义 | 首版要求 |
|---|---|---|
| Definition | 策划定义，以稳定 ID 和不可变 revision 寻址 | 物品模板、怪物模板、任务定义、NPC 定义、地图规则等必须版本化 |
| Instance | 运行时事实与状态 | 角色、背包物品、任务进度、战斗、副本、奖励记录不得由模板修改后隐式重算 |
| Presentation | 客户端视觉、音效和交互表现 | 不作为战斗、奖励、价格、任务完成的权威来源 |
| Release | 完整引用闭包和能力清单的不可变快照 | 激活、回退和实例绑定必须围绕 Release 进行 |
| Game | 一套具体游戏 | 首版提供原创 demo 游戏内容作为验收样例 |
| ContentPackage | 可组合使用的内容集 | 首版以 demo 内容包验证发布闭环 |
| Realm | 运营分服 | 首版每个 Realm 一个游戏写进程 |
| Revision | 某个内容草稿被固化后的版本 | 审批和构建只针对确切 revision |
| placement_id | Godot 导出的稳定空间锚点 ID | 网页通过它绑定 NPC、出口、触发器等规则 |

## 5. MVP 用户旅程

### 5.1 内容发布旅程：发布一个可奖励的物品

1. 内容作者在管理平台创建物品 Definition。
2. 系统校验字段、ID、引用、数值范围和素材引用。
3. 内容作者提交 revision。
4. 审核发布者查看差异和校验结果。
5. 审核发布者审批并构建 Release。
6. 游戏服务端确认激活 Release。
7. 玩家通过任务、副本或战斗获得该物品 Instance。
8. 后续修改物品 Definition 只能产生新 revision，不改变已获得的物品 Instance。

### 5.2 地图创作旅程：发布一张原创地图

1. 内容作者在 Godot 4.7.1 中创建原创 2D 正交网格地图。
2. 内容作者放置出生点、NPC 锚点、传送锚点、触发区或副本入口，并为每个锚点提供稳定 `placement_id`。
3. Godot 导出地图几何 revision，包括边界、通行格、锚点和区域。
4. 内容作者在网页管理平台将锚点绑定到 NPC、出口、任务目标或遭遇规则。
5. 系统校验锚点存在、引用完整、路径可达、不可支持几何被拒绝。
6. 审核发布者审批并激活 Release。
7. 玩家进入地图，客户端展示表现，服务端按格坐标权威校验移动。

### 5.3 NPC 任务旅程：接取并推进任务

1. 玩家靠近 NPC。
2. 玩家打开对话并选择明确选项。
3. 服务端校验距离、角色状态、任务前置、选项合法性和 Release 版本。
4. 玩家接取任务。
5. 玩家完成指定目标，例如击败指定遭遇或完成副本阶段。
6. 服务端根据可信事件推进任务进度。
7. 玩家回到 NPC 或触发交付条件。
8. 服务端以幂等事务发放奖励，一次操作只产生一笔有效奖励。

### 5.4 双人战斗/副本旅程

1. 两名玩家登录并进入同一 Realm。
2. 一名玩家创建队伍，另一名玩家加入。
3. 队伍通过 NPC、入口或任务进入副本。
4. 服务端创建副本 Instance，并绑定开始时的 Release。
5. 队伍进入回合制战斗。
6. 两名玩家提交各自授权命令；超时玩家使用默认行动。
7. 服务端排序、结算、生成事件序列并持久化关键结果。
8. 客户端只播放事件，不提交伤害值、掉落结果或任务完成事实。
9. 副本结束后，服务端结算奖励并记录操作结果。
10. 重连或服务重启后，不重复结算同一副本奖励。

## 6. 首版范围

### 6.1 必须包含

首版必须包含以下产品能力：

- 原创 demo 内容包。
- 至少 2 张原创地图。
- 至少 1 个角色原型和 1 个门派。
- 至少 2 个 NPC。
- 至少 2 种怪物。
- 至少 3 个基础技能；Buff 可作为额外内容。
- 至少 3–5 种物品。
- 至少 1 条三阶段任务。
- 至少 1 个多阶段双人副本闭环；单场双人战斗不能替代副本验收。
- 管理平台中的内容草稿、校验、revision、审批、构建、激活和审计基础能力。
- Godot 地图几何和锚点导出能力。
- Go 服务端的权威移动、任务、战斗、奖励和实例版本绑定。
- PostgreSQL 中的控制面与运行面必要数据。
- WSS + binary frame 中 UTF-8 JSON 的基础游戏协议。

### 6.2 首版明确不做

首版不包含以下内容：

- 不兼容或迁移 xyq 的旧客户端协议。
- 不迁移 xyq 玩家存档。
- 不分发缺少明确授权的 xyq 或第三方真实素材。
- 不承诺所有玩法永久零代码。
- 不允许运营平台上传任意 Go、Lua 或 GDScript 作为运行规则。
- 不建设 SQLite/MySQL 等多数据库适配。
- 不建设跨服、拍卖行、完整交易、公会、好友、宠物、坐骑、复杂活动或排行榜闭环。
- 不承诺不停服热更新；首版优先维护切换和安全激活。
- 不承诺未经压测验证的吞吐、在线人数或延迟指标。
- 不把 JSON textarea 当作最终内容编辑体验。
- 不把 Godot 中的 node path、资源 UID 或显示名作为跨端稳定主键。
- 不用客户端结果决定战斗胜负、奖励、任务完成或经济变更。

## 7. 内容支持等级

首版每项内容能力必须标记为 `supported`、`approximate` 或 `unsupported`。

| 等级 | 含义 | 发布策略 |
|---|---|---|
| supported | 当前 Schema、编辑器、服务端执行、客户端表现和测试均支持 | 可进入 Release 构建与激活 |
| approximate | 可被近似表达，但语义不完全一致 | 默认不得发布；必须人工确认并在验收中显式记录，首版不作为核心闭环依赖 |
| unsupported | 当前机制无法表达或无法安全执行 | 阻止发布，不允许静默降级 |

### 7.1 MVP 内容支持矩阵

| 内容族 | 首版支持等级 | 首版说明 |
|---|---|---|
| 地图/传送 | supported | 正交整数网格、边界、通行格、出生点、NPC 锚点、传送锚点和区域锚点 |
| 角色/基础成长 | supported | 至少一个角色原型，支持等级/属性读取和战斗单位生成；复杂养成延期 |
| 门派 | supported | 至少一个可用门派并与角色创建/成长关联；复杂门派生态延期 |
| 怪物/遭遇 | supported | 支持怪物属性、基础 AI、队伍编成和掉落引用 |
| 物品/装备 | supported | 支持基础物品、堆叠、奖励发放和背包持久化；复杂词条体系可后续扩展 |
| 技能/Buff | supported | 至少 3 个基础技能，支持目标选择、消耗、冷却、伤害/治疗/状态效果和事件表现绑定；多击语义只有实现独立 hit_count 执行器及逐击事件测试后才可标 supported，否则为 unsupported |
| NPC/对话 | supported | 支持服务、分支选项、接取/交付任务和传送/副本入口绑定 |
| 任务 | supported | 支持前置、指定目标、阶段状态、奖励和幂等交付 |
| 副本 | supported | 支持双人准入、阶段、遭遇和结算奖励 |
| 商店/制作 | unsupported | 非首版闭环必需，后续模块化交付 |
| 宠物/伙伴/坐骑 | unsupported | 后续独立纵切片 |
| 社交/交易/公会 | unsupported | 首版仅支持基础队伍，不支持玩家间交易和公会 |
| 活动/排行榜 | unsupported | 后续在可信时钟和运营规则成熟后交付 |
| xyq 导入 | unsupported | P7 以后可选；首版不依赖导入 |

## 8. 扩展能力边界

首版采用分层扩展承诺：

1. **新增已有机制下的内容**：只需新增或修改 Definition，例如新增物品、怪物、NPC、任务阶段、副本遭遇或地图锚点绑定。
2. **新流程组合现有原语**：可以通过已有 Condition、Action、Effect、Trigger/Event、Flow/StateMachine、Selector/Policy 组合表达，但必须通过校验和测试。
3. **新增机制、新交互或新表现**：必须增加版本化 Go handler、必要的 GDScript 表现模块、Schema、编辑支持和测试，不能仅注册一个字段就宣称可用。

内容发布系统必须在构建时阻止 unsupported 内容进入 Release。

## 9. 技术与产品约束

首版必须遵守以下已确认约束：

- 后端使用 Go 1.26.4 基线和 Leaf v2.0.3。
- 游戏客户端和地图创作使用 Godot 4.7.1。
- 管理前端使用 React + TypeScript + Vite + Tailwind 4。
- PostgreSQL 是唯一业务数据库；开发、测试、生产均不以 SQLite 替代集成验证。
- Go 服务端是战斗、奖励、任务状态、背包、经济和副本实例的权威来源。
- Godot 拥有地图几何、稳定 `placement_id` 和位置；网页管理平台拥有玩法规则绑定。
- Release 是不可变快照；实例必须绑定其实际依赖版本或闭包。
- 没有明确授权的素材不得进入可分发内容包。
- xyq 仅作为参考来源，不保证协议、存档、素材或实现兼容。

## 10. 关键验收指标

以下指标用于判断首版是否达到产品可用性，不包含未经压测验证的吞吐承诺。

### 10.1 玩家体验验收

- 两名玩家可以完成登录、组队、进入副本、回合战斗、结算奖励的完整 E2E。
- 玩家越界、穿墙、非法锚点交互、越权提交他人战斗命令均被拒绝。
- 战斗超时后服务端可执行默认行动，并继续推进战斗。
- 战斗和奖励结果由服务端生成，客户端不能伪造伤害、掉落或任务完成。
- 重连后玩家可看到与服务端一致的角色、任务、战斗或副本状态。

### 10.2 内容创作验收

- 内容作者可以创建或修改一个物品 Definition，并通过审批发布后在游戏内获得该物品。
- 内容作者可以导出一张原创地图，并在网页绑定 NPC、出口或副本入口。
- 内容作者配置 NPC 任务后，玩家可在游戏内接取、推进和交付。
- 引用缺失、锚点缺失、unsupported 机制、缺少授权素材等问题能在发布前被定位到字段或对象。
- 修改已有 Definition 会产生新 revision，不会原地改变旧 Release。

### 10.3 审核发布验收

- 审核发布者只能审批确切 revision。
- Release 构建包含完整引用闭包、能力清单、Schema/ruleset/protocol 版本和资产 manifest。
- 激活失败时旧 Release 继续有效。
- 回退只影响后续内容选择，不撤销已经提交的奖励或玩家资产。
- 审计记录能追踪草稿、校验、审批、构建、激活和回退操作。

### 10.4 数据一致性验收

- 同一奖励操作重复提交时，只产生一笔有效奖励。
- 相同幂等键但不同 payload 必须被拒绝。
- 提交前失败不提示成功，提交后推送失败可恢复已提交结果。
- 服务重启后不会重新随机生成已承诺的战斗或掉落结果。
- 旧副本、旧任务和旧物品实例保留其依赖的 Release 或 Definition 闭包。

## 11. 可映射 E2E 场景

后续 E2E 应至少覆盖以下场景：

1. **物品发布到获得**：管理平台创建物品 → 审批发布 → 玩家完成任务 → 背包出现一件对应物品 Instance。
2. **地图发布到进入**：Godot 导出原创地图 → 网页绑定出生点和 NPC → 审批发布 → 玩家进入地图并被服务端阻止穿墙。
3. **NPC 任务闭环**：配置 NPC 对话和任务 → 玩家接取 → 击败指定目标 → 回 NPC 交付 → 奖励只发一次。
4. **双人副本闭环**：两名玩家组队 → 进入副本 → 回合战斗 → 副本结束 → 两名玩家获得符合规则的奖励。
5. **发布失败保护**：构建或激活失败 → 旧 Release 仍可服务玩家。
6. **unsupported 阻断**：内容作者配置首版未支持机制 → 校验失败 → 不能构建 Release。
7. **实例版本保护**：修改物品或任务定义并发布新 Release → 旧实例仍按旧闭包结算或展示。
8. **重启恢复**：战斗或奖励提交关键点前后模拟失败 → 恢复后不丢成功提交结果，不重复奖励。

## 12. 依赖

首版产品落地依赖：

- PostgreSQL 开发、测试和运行环境。
- Go 1.26.4 工具链与 Leaf v2.0.3。
- Godot 4.7.1 编辑器、headless 能力和匹配导出模板。
- React + TypeScript + Vite + Tailwind 4 管理前端基础工程。
- JSON Schema 校验能力：Go 服务端和 React/AJV 侧必须对核心 fixtures 一致。
- 原创或明确授权的 demo 素材，包括地图、角色、NPC、怪物、物品图标和基础表现资源。
- 可执行的内容发布链路：校验、构建、manifest、staging、激活和审计。
- 后续架构文档对 owner、事务、协议、Release 和故障恢复策略的详细定义。

## 13. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 试图首版支持所有玩法 | 范围失控，无法验收 | 只交付 MVP 闭环；使用 supported/unsupported 门禁 |
| 内容与表现字段双真源 | 发布内容与游戏表现不一致 | Godot 只拥有几何/位置，网页只拥有规则绑定 |
| 客户端作弊或伪造结果 | 奖励、战斗和经济被破坏 | Go 服务端权威执行，客户端只提交意图和播放事件 |
| 发布破坏旧实例 | 玩家资产或任务状态异常 | Release 不可变，实例绑定依赖闭包，破坏性变更需迁移或拒绝 |
| 重复发奖 | 经济系统失真 | PostgreSQL 事务、幂等键、operation result 和 outbox 幂等消费 |
| 素材授权不清 | 无法分发或存在法律风险 | 首包只用原创或明确授权素材；缺授权即阻止发布 |
| xyq 参考被误用为兼容承诺 | 协议、存档或语义错误 | 文档和校验中明确 xyq 仅参考，不迁移旧协议/存档 |
| PostgreSQL 集成不足 | 测试通过但生产行为不一致 | 集成和故障验收必须使用真实 PostgreSQL |
| 未验证性能承诺 | 误导计划和发布判断 | 首版只记录实测环境和结果，不预设吞吐宣传指标 |

## 14. 发布判定

满足以下条件后，首版可被认为达到 MVP 产品验收：

- 原创 demo 内容可通过管理平台和 Godot 创作链路发布为 Release。
- 两名玩家能完成 NPC → 任务 → 组队 → 双人战斗/副本 → 奖励的完整闭环。
- 关键非法操作、重复提交、发布失败、重启恢复和 unsupported 内容均有可执行验收。
- 内容作者能在已有机制范围内新增至少一个物品、一个 NPC 任务或一个怪物遭遇，无需改运行时代码。
- 审核发布者能审查、审批、激活和回退后续内容选择，并保留审计记录。
- 所有可分发素材均为原创或有明确授权记录。
